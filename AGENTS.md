# Agent Instructions

## Overview

Read the project name and description from [`project-context.toml`](project-context.toml); run `python3 scripts/project_context.py` to validate it. Feature specs, plans, and tasks are organized in the `specs/` directory. Governance rules are defined in [`.specify/memory/constitution.md`](.specify/memory/constitution.md) and are not overridden by project context.

## Non-Negotiable Guidance

- **Prefer `gh` cli tool over Github MCP, if possible**
- **Hard rule: check roadmap dependencies before starting or resuming implementation.** Invoke the [roadmap-dependency-check skill](.agents/skills/roadmap-dependency-check/SKILL.md) before implementing, creating Phase/implementation branches, moving a Phase issue to In Progress, or launching agents for implementation. Follow it for entry resolution, prerequisites, blockers, overrides, and implementation resume checks; if the skill or required hook configuration is unavailable, stop and resolve that first. Before specifying, [roadmap-entry-check](.agents/skills/roadmap-entry-check/SKILL.md) requires an explicit feature directory and planned entry identity, warns about blockers without requiring acknowledgement, and stops on errors. Dependency acknowledgement does not block specification branches, clarify, plan, tasks, analyze, or converge. Standalone repository chores unrelated to a roadmap item do not need an invented entry. This gate does not replace any other workflow or approval rule.
- **Roadmap IDs are feature IDs.** Before `speckit-specify`, explicitly supply `SPECIFY_FEATURE_DIRECTORY=specs/<roadmap-id>-<slug>` so the directory prefix matches the roadmap entry. For example, entry 008 uses `SPECIFY_FEATURE_DIRECTORY=specs/008-example-feature`; do not use the next free sequential number.
- **Roadmap issues are synchronized by CI.** The **Sync Roadmap to GitHub Issues** workflow creates or reconciles each planned entry's Epic, spec-plan planning issue and provisional Phase 1 issue after roadmap or spec artifacts change on `main`. Review its dry run during rollout; do not recreate or repair these issues manually. Before specifying, use the `SPEC: <ID> Create and approve spec and plan` issue for the issue-backed spec-and-plan branch. There is no separate tasks-planning issue: after the spec-and-plan pull request merges, use the provisional Phase 1 issue for task generation and implementation.
  - The workflow finds roadmap and planning issues by markers, not titles.
  - If an expected planning issue is missing, first inspect the latest **Sync Roadmap to GitHub Issues** run and its dry-run output; never create a duplicate manually.
  - See the [roadmap item walkthrough](scripts/README.md#roadmap-item-walkthrough).
- **Hard rule: spec and plan merge before tasks.** For a new feature, `spec.md` and `plan.md` (with research, data model, contracts, quickstart) go in their own pull request. Do not run `speckit-tasks` until that PR is merged and `main` is pulled; then generate tasks on the Phase 1 implementation branch (there is no separate tasks pull request or tasks planning issue). The `before_tasks` hook `plan-merged.check` (skill `plan-merged-check`) enforces this; if it fails, stop and tell the user. Never bypass it, and never add the `combined-spec-pr-approved` label yourself. The separate `prerequisites-acknowledged` label for a known dependency blocker is human-only: agents and automation must never apply it.
- **Hard rule: run Spec Kit workflow steps only through the `speckit-*` skills, and run their hooks.** Invoke the skill (e.g. `speckit-specify`, `speckit-clarify`, `speckit-plan`, `speckit-tasks`, `speckit-analyze`, `speckit-converge`, `speckit-implement`); do not hand-edit `spec.md`, `plan.md`, or other Spec Kit artifacts. During implementation, `tasks.md` may be maintained directly in reviewed implementation PRs as described below.
  - Before each skill, re-read `.specify/extensions.yml` (also after a context reset) and run every enabled `before_<step>` hook; after it, every enabled `after_<step>` hook, in listed order.
  - `optional: false` hooks are mandatory: run them without asking, and never skip, reorder or substitute them. Ask the user about `optional: true` hooks; never skip them silently.
  - If a hook fails or cannot run, stop, show the failure and wait for the user. Never edit `extensions.yml` to get past a hook.
  - End every Spec Kit step with one line, `Hooks run: <hook>: <ran|skipped|failed>, ...`, listing every hook for that step, including skipped and failed ones.
- **Hard rule: follow the Spec Kit step order:** specify → clarify → plan → tasks → analyze → implement. Never skip or reorder steps. Do not use `.specify/workflows/`; it is not part of this project's process. Clarify (the `after_specify` hook) may be skipped only when the user explicitly says the work is an exploratory spike; record it as `speckit.clarify: skipped (spike, per user)`.
  - **Spec review gate:** after clarify, stop and ask the user to review and approve the spec before `speckit-plan`.
  - **Plan review gate:** after `speckit-plan`, the spec and plan go through their pull request (see the spec-and-plan rule above) before tasks.
  - **Tests in `tasks.md`:** the constitution's quality gate overrides the `speckit-tasks` default that tests are optional. When the constitution or spec requires automated tests, every behavior change gets a test task written before its implementation task.
  - **Implementation gate:** after analyze, report its findings and resolve CRITICAL ones. Implement only after the spec-and-plan pull request is merged and the user approves. Verify the merge with `git` and `gh` before starting. Do not require a GitHub Phase sync before implementation: Phase 1 tasks are generated on the Phase 1 implementation branch, and the Phase issues sync after the implementation PR merges. Phases are the only issues generated from `tasks.md`; `T###` tasks never become issues. Never run the deprecated `speckit-taskstoissues` skill or the Spec Kit `github` extension's `speckit-github-taskstoissues`: they create one issue per task, and the phase sync owns all issues. Direct `tasks.md` maintenance is allowed in reviewed implementation PRs; rerun `speckit-analyze` after structural edits (Phases, tasks, dependencies), not after checkbox-only or wording changes.
  - When a step finishes, the next proposed action is the next step, not committing or opening a pull request; in particular, analyze runs right after the initial `speckit-tasks` generation, before implementation starts.
- **Roadmap.** [`ROADMAP.md`](ROADMAP.md) at the repository root is the plan-only ledger. Validate it with `python3 scripts/check_roadmap.py`; its format is documented in [`docs/roadmap-format.md`](docs/roadmap-format.md).
  - The main session owns exactly three roadmap hooks in `.specify/extensions.yml`: mandatory `roadmap-entry.check` before specifying (entry must be planned and `SPECIFY_FEATURE_DIRECTORY` must match; dependency blockers are warnings), mandatory `roadmap-dependency.check` before implementing (blocks on unfinished prerequisites), and optional `roadmap.write` after a constitution change. Run applicable hooks once per feature or phase, never per `tdd-implementer` slice.
  - The main session runs the dependency guard before delegating roadmap work and gives `tdd-implementer` the entry, requested scope, any verified milestone evidence, blockers, and any explicit acknowledgement (or confirms there are no blockers). The agent stops if this result is missing; it does not invent or broaden an override.
  - `ROADMAP.md` uses plan statuses only: `undecided`, `needs-info`, `planned`, `deferred`, `abandoned`. Read progress with `python3 scripts/roadmap_status.py` or on the board; use `python3 scripts/roadmap_status.py --id <ID> --json` for dependency checks. Only an Epic closed as completed satisfies ordinary completion; missing Epics, open Epics and closure as not planned do not. Historical notes and board Status are not completion evidence.
  - The `roadmap-entry.check` hook requires an explicit `SPECIFY_FEATURE_DIRECTORY=specs/<ID>-<slug>` and a matching `planned` entry; it warns about blockers but does not acknowledge them. The `roadmap-dependency.check` hook rechecks live GitHub completion before implementation and blocks unless the user explicitly acknowledges the exact blocker set.
  - [`roadmap-write`](.agents/skills/roadmap-write/SKILL.md) is the only skill that edits `ROADMAP.md`. The `prerequisites-acknowledged` label is human-only, applies only to the known blockers reported for that Phase PR, and never overrides invalid data or ambiguous identity.
- **Delegated implementation.** When tasks are implemented through `tdd-implementer` without a `speckit-implement` run, the main session runs the `before_implement` hooks before the first task, and the `after_implement` hooks, in order, after the last task of each phase and before the pull request.
- **Hard rule: always ask the user before committing.** Never run `git commit` (or amend/squash) without explicit approval for that commit; this includes commits between tasks. Show a summary of the changes and the proposed commit message when asking.
- **Always pull `main` before creating a new branch** (a new feature, Phase or issue): run `git fetch origin && git checkout main && git pull --ff-only origin main` (stash or ask the user first if the working tree is dirty), then create the issue-backed branch from the freshly pulled `main`. Continuing on the issue-backed branch linked to the Phase issue being implemented, including the next `T###` task or implementing right after `tasks.md` was generated there, is not new work: run `git fetch origin` to compare dependency data with `origin/main`, but do not stash or switch to `main`.

## Agents

Sub-agents live in [`agent-definitions/`](agent-definitions/). Delegate to one when its trigger below applies. They do not replace the Spec Kit skills or the hard rules above. Model and reasoning effort per tool are set in [`agent-definitions/agents.toml`](agent-definitions/agents.toml), because model names differ per tool; see that file for each agent's profile and values.

The team uses Copilot, Codex and Claude Code, and every skill and sub-agent exists once (README "Coding agents"):

- **Skills live only in `.agents/skills/`; sub-agents only in `agent-definitions/<name>.md`.** `.claude/skills` is a symlink to the skills. `.github/agents/*.agent.md`, `.claude/agents/*.md` and `.codex/agents/*.toml` are generated locally from the sub-agents and `agents.toml` (by `npm ci`, or `python3 scripts/agent_setup.py sync`; no Git hook regenerates them) and are gitignored; never edit them by hand. `npm run setup-agents`, `sync --tool <name>` or `git config agent-setup.tools copilot` limits generation to some tools. The three folders are git-ignored as a whole; keep personal agents in your user-level folder (for example `~/.claude/agents/`). Never copy a skill or sub-agent into another folder, and never recreate `.github/skills/`.
- **Never edit Spec Kit-generated files by hand** (files listed in `.specify/integrations/*.manifest.json`, or skills generated by a Spec Kit extension). Change them only with `scripts/specify.sh`, which runs the pinned Spec Kit version, in a pull request of their own.
- **After changing anything in `agent-definitions/`, run `python3 scripts/agent_setup.py sync`.** Before committing agent or Spec Kit changes, run `python3 scripts/agent_setup.py check`; CI runs it too.

| Agent                                                                     | Role                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`tdd-implementer`](agent-definitions/tdd-implementer.md)                 | Builds the given task IDs red-green-refactor, updates the docs the change invalidates, runs the area's full checks and marks only its own finished tasks `[x]`. Never commits.                                                                 |
| [`code-reviewer`](agent-definitions/code-reviewer.md)                     | Reviews a diff or PR against the spec and constitution across correctness, readability, architecture, security and performance. Given a PR number or URL, posts inline comments as one GitHub review. Runs lint/typecheck/tests only if asked. |
| [`test-engineer`](agent-definitions/test-engineer.md)                     | Designs tests, audits coverage against the constitution's quality gate, writes Prove-It reproductions for bugs and checks that guard tests can actually fail.                                                                                 |
| [`security-auditor`](agent-definitions/security-auditor.md)               | Report-only security pass: authentication and server-side authorization, infrastructure permissions, secrets, input handling, dependencies and supply chain; check the constitution's technology baseline.                                      |
| [`web-performance-auditor`](agent-definitions/web-performance-auditor.md) | Report-only web performance audit of the project's web front end: Core Web Vitals, loading, rendering and network. Use when performance is the question, not on every change.                                                                   |

The mandatory review gate is the `code-review-and-quality` skill, run through `code-reviewer`, on the exact final diff before a pull request is created (see "When Creating a Pull Request"), plus the independent non-author human approvals the constitution's Git workflow principle requires, mirrored in `[review] required_approvals` in `project-context.toml` (default 1; 0 is valid only where the constitution allows a solo project, and the constitution wins if they differ). `code-reviewer` also reviews each task's diff after `tdd-implementer` has run; `tdd-implementer` never reviews its own work and skips the `after_implement` `code-review-and-quality` hook, which remains as a safety net for anyone who runs `speckit-implement` directly; the other agents are invoked on demand. Run `security-auditor` for security-sensitive changes (the constitution's security principle) and before the first deployment. `code-reviewer`, `test-engineer`, `security-auditor` and `web-performance-auditor` are adapted from [addyosmani/agent-skills](https://github.com/addyosmani/agent-skills) `agents/`; each file names the upstream commit it came from. `tdd-implementer` is local to this repository.

### Which agent takes which task

| The task is...                                                                                           | Give it to                                                                             |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| An implementation, with or without its own test                                                          | `tdd-implementer`                                                                      |
| Test-only: "write a failing test…", an end-to-end or round-trip test, a bug reproduction                 | `test-engineer` (stops at red), then `tdd-implementer` for the implementation          |
| A coverage audit, or "can this guard test actually fail?" after a task                                   | `test-engineer`                                                                        |
| A review of a diff, a task or a pull request                                                             | `code-reviewer`                                                                        |
| A security pass on auth, permissions, IAM, secrets or infrastructure-as-code changes                     | `security-auditor`                                                                     |
| A performance question about the web front end                                                           | `web-performance-auditor`                                                              |
| Specifying, clarifying, planning or breaking work into tasks                                             | The `speckit-*` skills in the main session, no agent                                   |
| Running something: the CI checks, the quickstart walkthrough, a deploy to the constitution's dev environment | The main session, no agent                                                         |

Rules that keep agents from colliding:

- **One agent per task ID.** `tdd-implementer` and `test-engineer` both start by writing the failing test, so giving both the same ID produces two sets of tests.
- **One writer per file at a time.** `[P]` in `tasks.md` is meant to say the tasks touch different files. Where several `[P]` tasks target the same file, run them in sequence with one agent; parallel agents would lose each other's edits, as they do on `tasks.md`.
- **`test-engineer` stops at red and reports; `tdd-implementer` takes it to green.** Run them one after the other, never together. Tell `test-engineer` in the prompt to write tests only, not to touch production code. When the tests came first, `tdd-implementer` confirms they fail before implementing and does not edit them.
- **The caller owns `tasks.md` when more than one agent works at once.** Say so in the prompt; the agent then reports finished task IDs instead of marking them. `test-engineer` never marks tasks.
- **Agents do not call each other.** Reviewers and auditors recommend follow-up passes in their report; the caller starts them.
- **The caller relays every review and audit finding to the user.** For `code-reviewer`, fix Critical and Required findings; for `security-auditor`, `test-engineer` and `web-performance-auditor`, fix Critical and High findings. Pass the fixing work to `tdd-implementer` whenever possible. If you believe a finding is wrong, show it to the user with your reasoning instead of fixing it. Show every other finding (Optional, Nit, FYI, Medium, Low, Info) to the user, with file:line where it has one, and let the user decide; never fix or dismiss them silently.
- **Agents never commit, push or open pull requests.** The user approves every commit.

## Project Instructions

### Conditional Impact Analysis

When a change renames or removes an identifier, changes configuration semantics, alters shared interfaces or behavior, or touches authentication, authorization, or path checks:

- Search the repository for affected names and behavior, including application and infrastructure code, `scripts/`, specs, documentation, tests, CI, and error messages. Update active references; preserve historical records where appropriate.
- For environment-variable changes, check every consumer, including runtime code, tests, infrastructure, and docs. Preserve backward compatibility when the old behavior was supported, or document the breaking change. Use a default only when it is safe and semantically correct; fail clearly when required configuration is missing.
- For authentication, authorization, and path checks, validate untrusted inputs and use consistent path normalization and method handling where relevant.
- When tests modify `process.env`, snapshot and restore it with `{ ...process.env }`. After renames or refactors, check for stale references and orphaned imports or code.
- Run the relevant tests and project checks for the affected area. Use the scripts defined in that area’s `package.json` and the applicable CI checks.

### Implementing Tasks from tasks.md

- **Prefer completing a whole phase at once if possible.** If not, focus first on the tasks that are blockers for other tasks.
- **Never go beyond the requested task or phase.**
- **Mark only the finished task as done in `tasks.md`.**
- **If working on a whole phase in a single session, don't mark single tasks completed in GitHub in between tasks.**
- **Between tasks, propose a meaningful commit message and commit once the user approves. If the tasks becomes large, eg. over 10 files or hundreds of lines of code, propose multiple commits.**
- **After editing or creating a file, run the supported code formatter, eg. Prettier**
- **Work on the branch linked to the Phase issue.** Individual `T###` items do not have GitHub issues or branches. Before suggesting or creating a branch, look up the Phase issue number and title. Use `<github-issue>-phase-<phase-number>-<kebab-case-title>` or retain GitHub's full-title branch suggestion, which includes `phase-<phase-number>` in the slug.
- **Do not invent a task ID.** For repository work that is not a Spec Kit task, create an issue whose title starts with `CHORE:`, `CI:`, `DOCS:`, `FIX:`, `REFACTOR:`, `SPEC:`, or `TEST:` and use `<github-issue>-<lowercase-type>-<kebab-case-title>`.
- **Create linked branches with GitHub's issue "Create branch" action or `gh issue develop <issue> --base main --name <branch> --checkout`.** If the current branch is `main`, ask the user to create or approve creation of the issue-backed branch before editing.

### When Starting New Work

- **For Phase implementation, use the Phase issue as the work item.** Assign the user and move that issue to "In Progress" using the API (`gh` CLI). Do not create or assign GitHub issues for individual `T###` tasks.
- **Starting a roadmap item:** follow the roadmap dependency and issue-backed planning rules above. Use its spec-plan planning issue for the spec-and-plan branch and the provisional `Phase 1: Kickoff — <Epic name>` story for the Phase 1 implementation branch, where `tasks.md` is generated (for example, `<issue>-spec-008-create-and-approve-spec-and-plan`); assign the user and move the issue to In Progress as above.

### When Creating a Pull Request

- **Before creating or opening any pull request, run the `code-review-and-quality` skill on the exact final diff, preferably through the `code-reviewer` agent.** Fix its Critical and Required findings (passing the work to `tdd-implementer` whenever possible; if you believe a finding is wrong, show it to the user with your reasoning instead of fixing it) and show its Optional, Nit and FYI findings to the user for a decision; if the diff changes after review, rerun the review on the updated diff. Do not create or open the pull request until the review is complete.
- **When tasked to create a pull request, also move the issue to the "In Review" column** using the API (`gh`- cli tool).
- **Link the issue in the pull request body.** For a non-Phase issue branch, include `Closes #<github-issue>`; for a Phase branch, use `Part of #<phase issue>` instead, because a Phase PR is often partial and a closing keyword would close the Phase on merge. The Phase sync closes a Phase when all its tasks are checked and reopens it when unchecked tasks remain. The PR conventions workflow derives the issue from the validated branch name and adds the right line when it is missing (it leaves a closing keyword the author wrote on a Phase PR alone, because the Phase sync reopens an incomplete Phase).

### Approvals

- **Approvals are enforced by the branch ruleset** with the count from `[review] required_approvals` in `project-context.toml` (default 1; 0 is valid only where the constitution allows a solo project). The constitution sets the count; `required_approvals` mirrors it, and the constitution wins if they differ. GitHub records each review (reviewer, state, reviewed commit, time) on the pull request; nothing is written into spec, plan or task documents.
- **To see who approved a change,** find its pull request (the merge commit names it) and run `gh pr view <n> --json reviews --jq '.reviews[] | "\(.author.login) \(.state) \(.commit.oid[0:7]) \(.submittedAt)"'`. Count only reviews whose state is `APPROVED` and whose author is not the PR author.
